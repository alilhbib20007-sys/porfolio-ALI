SonarQube Cloud et le Quality Gate

SonarQube Cloud analyse automatiquement la qualité et la sécurité du code. Intégré à GitLab CI/CD, il intervient avant le déploiement :

  1. Le développeur pousse son code sur GitLab.
  2. GitLab déclenche le pipeline CI/CD.
  3. Le scanner analyse le code et envoie les résultats à SonarQube Cloud.
  4. SonarQube calcule les métriques et évalue le Quality Gate.
  5. Si le Quality Gate échoue, le job échoue et le déploiement ne s'exécute pas.
Métrique Ce qu'elle mesure
Bugs (fiabilité) Défauts pouvant provoquer un comportement incorrect
Vulnerabilities (sécurité) Failles exploitables, par exemple une XSS via innerHTML
Security Hotspots Code sensible à vérifier par un humain
Code Smells (maintenabilité) Code difficile à comprendre ou à modifier
Coverage Part du code exécutée par les tests (non utilisée ici)
Duplications Code répété

Le Quality Gate (« Sonar way ») est l'ensemble des conditions que le code doit respecter. Avec sonar.qualitygate.wait=true, le scanner attend le verdict et fait échouer le job si le Quality Gate est rouge.

Étape 3 : pipeline V1 (deux jobs)

stages:
  - quality
  - deploy

variables:
  GIT_DEPTH: "0"
  SONAR_USER_HOME: "${CI_PROJECT_DIR}/.sonar"

sonarqube-check:
  stage: quality
  image:
    name: sonarsource/sonar-scanner-cli:latest
    entrypoint: [""]
  script:
    - sonar-scanner
      -Dsonar.host.url="$SONAR_HOST_URL"
      -Dsonar.token="$SONAR_TOKEN"
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

deploy-pages:
  stage: deploy
  image: alpine:latest
  script:
    - mkdir -p public
    - cp index.html style.css script.js public/
    - test -s public/index.html
  pages:
    publish: public
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
git add .
git commit -m "V1 - code correct"
git push

Résultat V1 : sonarqube-check ✅ puis deploy-pages ✅. SonarQube : Quality Gate Passed, 0 problème de sécurité, de fiabilité ou de maintenabilité. Le site est publié sur GitLab Pages.

Problèmes rencontrés et solutions

Problème Cause Solution
Before you can run pipelines, we need to verify your account Compte GitLab récent Vérification du compte GitLab, puis nouveau pipeline
Organization is not allowed to access data from non main branches Le projet SonarQube créé manuellement avait master comme branche principale, alors que GitLab utilise main Branche principale SonarQube renommée en main
Quality Gate « Not computed » à la première analyse Pas encore de référence pour le new code Relance du pipeline : le Quality Gate est calculé
You are running CI analysis while Automatic Analysis is enabled (cas du support) Analyse automatique et analyse CI en même temps Administration → Analysis method : désactiver Automatic Analysis (déjà désactivée pour un projet manuel)

Étape 4 : V2 volontairement vulnérable (XSS)

Le formulaire envoie la saisie dans l'URL (?message=...) et le script l'insère comme du HTML :

<form id="demo-form">
  <label for="user-input">Votre saisie</label>
  <input id="user-input" name="message" type="text" autocomplete="off">
  <button type="submit">Afficher</button>
</form>
<p id="message" aria-live="polite"></p>
// script.js - V2 volontairement vulnérable (XSS DOM)
const message = new URLSearchParams(window.location.search)
  .get("message");

document.getElementById("message").innerHTML = message;

Une saisie comme <img src=x onerror="document.body.insertAdjacentHTML('beforeend','<h2>Injection persistante</h2>')"> est exécutée par le navigateur : c'est une injection XSS.

Remarque : une première version lisait input.value dans le formulaire. SonarQube ne l'a pas signalée, car son analyse de taint suit les données venant d'une source non fiable reconnue (ici l'URL : location.search) jusqu'à un point dangereux (innerHTML). Avec la source URL, la faille est détectée.

Pipeline V2 avec quatre jobs (syntax-check, sonarqube-check, security-check, deploy-pages) :

  - quality
  - security
  - deploy

syntax-check:
  stage: quality
  image: node:22-alpine
  script:
    - node --check script.js

sonarqube-check:
  stage: quality
  script:
    - sonar-scanner -Dsonar.host.url="$SONAR_HOST_URL" -Dsonar.token="$SONAR_TOKEN" -Dsonar.qualitygate.wait=true

security-check:
  stage: security
  image: node:22-alpine
  script:
    # interroge l'API SonarCloud : vulnérabilités ouvertes et hotspots à revoir
    # process.exitCode = 1 s'il en reste
git add .
git commit -m "V2 - injection xss"
git push

Résultat V2

  • syntax-check ✅ : le JavaScript est syntaxiquement valide.
  • sonarqube-check ❌ : SonarQube détecte « DOM XSS via unsanitized user input » (règle jssecurity:S5696, sévérité Blocker, script.js ligne 7). Note de sécurité E, Quality Gate Failed (new_security_rating = 5, seuil 1).
  • security-check et deploy-pages : skipped. Le code vulnérable n'est pas déployé, la V1 reste en ligne.

Conclusion

  1. Push vers GitLab : le développeur envoie son code.
  2. Pipeline déclenché automatiquement.
  3. Analyse SonarQube : bugs, sécurité, maintenabilité.
  4. Quality Gate : avec sonar.qualitygate.wait=true, un échec fait échouer le job quality.
  5. Déploiement bloqué : deploy ne s'exécute pas.
  6. Correction : on corrige (par exemple textContent au lieu de innerHTML), puis un nouveau push relance le pipeline.

À retenir : GitLab CI/CD automatise les étapes, SonarQube contrôle la qualité du code, et le Quality Gate empêche le déploiement d'un code qui ne respecte pas les critères définis.
